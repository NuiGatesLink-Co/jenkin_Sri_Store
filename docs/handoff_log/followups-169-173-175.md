## 1. #169 — the global idempotency cleanup deleted nothing

- **Bug confirmed on real Postgres.** The new e2e (`worker-jobs.e2e-spec.ts`, `#169`) seeds expired and fresh keys in two tenants, then waits on the **rows**. Against the old processor it times out.
- **Fix.** `MaintenanceProcessor.handleIdemCleanup` with no tenant runs `SELECT id FROM tenants` on the pool (`tenants` has no RLS) and `addBulk`s one `idem.cleanup` per tenant. Every DELETE now goes through `TenantJobRunner`, which gives it RLS, the suspended-tenant skip, retries and the DLQ.
  - Child job ids are `idem-cleanup-<parentId>-<tenantId>`, so a retried parent does not fan out twice. BullMQ job ids must not contain `:`.
  - `ADMIN_DATA_SOURCE` was rejected: it bypasses all three protections above.
- 🔴 **Nothing schedules the global job yet.** Expired keys (including #163's plaintext enrolment codes) are only removed when someone enqueues it. Add a BullMQ job scheduler when wanted; `server/README.md` *Idempotency* says so.

## 2. #175 — lost void-denial audit rows: not reproducible for role denials

Measured on the **old** 2 s timeout, at `DB_POOL_SIZE=2` with an audit pool of 2 connections, using concurrent cashier (role) denials:

| Plan | Burst | 403 | Rows | Wall time |
|---|---|---|---|---|
| `demo` (route limit 300/min) | 300 | 300 | 300 | ~0.85 s |
| `loadtest` (no limit) | 700 | 700 | 700 | 6.1 s |
| `loadtest` | 1000 | 1000 | 1000 | 6.2 s |

A burst of 1,500 failed on the supertest client's own sockets, not on the server.

**Why no loss:**
- The per-tenant limit keys on the **route pattern** (`req.route.path`), so role and no-PIN denials are capped per tenant.
- The single lost row in #154's review came from wrong-PIN denials, when argon2 was starving the event loop. `consumeAttempt` now caps those at 5 per user.

**What changed:**
- The 2 s timeout's stated reason ("the caller still holds its request connection") has been false since tx.5, so the timeout is now 10 s.
- No per-user role-denial counter and no audit queue were added; the measurements above show no loss to fix.
- `test/void-denial-burst.e2e-spec.ts` is a **regression pin, not a reproduction**. It also passes on the old code. `PROBE_PLAN=loadtest PROBE_BURST=1000` re-measures without the route limit.

## 3. #173 — cache hits no longer take a pooled connection

**Shape:** the public cached method does the cache work, then a `runTx` loader runs only on a miss, then the value is stored.
- `tenantId = authorisedTenantId()`, then `cache.prefix` (still before the query), then `get`, then `singleFlight`.
- On a miss: `await this.xUncached()`, whose `runTx` commits, then `cache.set`.
- The stampede lock is still released in `finally`.
- Loaders:
  - `ProductsService.listUncached` and `ProductsService.byIdUncached` (new)
  - `CategoriesService.list`
  - `SettingsService.getSettings`

**Measured** with `test/cache-hit-no-connection.e2e-spec.ts` at pool 2:

| Check | Old code | New code |
|---|---|---|
| `createQueryRunner` calls per HIT | 1 on each of the 4 routes | 0 |
| `pos_app` backends `idle in transaction` during a 4-request single-flight burst | 2 (the whole pool) | 0 |

Full e2e: 460 passed.

🔴 **`tenant-wrapper.spec.ts` did not change, and that is correct:**
- The cached methods no longer read `currentRequestContext()`.
- Every loader that does read it is a whole-body wrapper.
- A future cached read should follow this shape. Do **not** put the cache steps back inside `runTx`, and do not open `runTx` before `singleFlight`: a waiter would sit idle in a transaction again.

**Left out:** the backup/purge owner-role checks that run inside `runTx` before a 403. The issue calls them the "same class" of cost; there is no ticket.
